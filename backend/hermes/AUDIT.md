# Аудит Hermes Agent → оркестратор демо-сценария

Оценка [`NousResearch/hermes-agent`](https://github.com/NousResearch/hermes-agent) (MIT) как базы
роли «Hermes» — оркестратора ограниченного демо-сценария + Telegram-туннель
(см. `docs/ARCHITECTURE.md` §5.6, `docs/ROADMAP.md` Этап 7a).

> Статус: **только аудит и план**. Код не вендорился.

---

## 1. Что это по факту

Самоулучшающийся AI-агент от Nous Research — не узкое приложение, а **большой general-purpose
агент-фреймворк**. Клон ~**212 МБ, ~8067 файлов**; ядро огромное: `cli.py` 835 КБ, `run_agent.py` 337 КБ,
`hermes_state.py` 384 КБ, `.env.example` 24 КБ.

| Аспект | Значение |
| --- | --- |
| Язык/рантайм | Python **3.11–3.13** (`uv`) + Node.js **≥20**; ripgrep, ffmpeg |
| Модель | **Model-agnostic**, без локальной LLM/GPU: Nous Portal / OpenRouter / OpenAI / свой endpoint (`hermes model`) |
| Точки входа | `hermes` (CLI/TUI) и `hermes gateway` — **нативный мессенджер-gateway** |
| Каналы gateway | **Telegram**, Discord, Slack, WhatsApp, Signal, Email, Teams, Google Chat — из одного процесса |
| Состояние | SQLite (FTS5-поиск по сессиям), память/профили, learning loop |
| Упаковка | Docker (s6-overlay, `network_mode: host`) + dashboard (localhost, хранит API-ключи); установщик `curl … | bash` ставит uv/Python/Node |
| Лицензия | **MIT** (deps exact-pinned — осознанная защита от supply-chain) |

**Фичи (для нас — в основном избыточные):** автосоздание навыков из опыта, самоулучшение навыков,
Honcho-моделирование пользователя, cron-планировщик, subagents/параллелизм, batch-траектории и их сжатие
для обучения моделей, 7 terminal-backend'ов (local/Docker/SSH/Singularity/Modal/Daytona/Vercel),
desktop-приложение (`apps/` 27 МБ), web-UI (`web/`), сайт (`website/` 27 МБ), тесты (27 МБ),
`optional-mcps` / `optional-skills` / `plugins`.

## 2. Принципиальное отличие от FlowDesk-AI

FlowDesk (диспетчер) — маленький, целевой; его **вендорят и подрезают** в `backend/dispatcher/`.
Hermes — **наоборот**: тяжёлый фреймворк широкого назначения. Вендорить 212 МБ / 8067 файлов в
`Labs_Solutions` **нельзя и не нужно**. Правильный путь:

> **Использовать как внешнюю зависимость** — устанавливать на VPS штатным установщиком/`uv` с
> **зафиксированной версией** (pin) `hermes-agent==0.19.0` (pyproject) / npm `1.0.0`, а в репозиторий
> парка класть только **тонкий слой конфигурации** (профиль, скилл-сценарий, toolset-lockdown, env),
> а не сам код агента.

## 3. Убрать / выключить (лишнее и опасное для публичного демо)

### 3.1. Безопасность — главный пункт
Hermes — автономный агент с доступом к **terminal/file/browser** (в `toolset_distributions.py` профили
с `"terminal": 100`). Для **публичного клиентского демо это недопустимо**. Обязательно:
- **Safe mode без terminal** (в репо есть профиль «All tools except terminal for safety») + жёсткий
  whitelist toolset'а: только RPC-инструменты демо-сценария (dispatcher → OCR → RAG → PDF), без произвольного shell.
- Включить встроенные механизмы: **command approval**, **DM pairing**, **container isolation**
  (у Hermes это есть из коробки — Security docs).
- Стоп перед критичными действиями (human-in-the-loop) — совпадает с ролью «Hermes» из `Контекст_…md` и §6.

### 3.2. Отключить лишние подсистемы для MVP-демо
- Каналы gateway — **оставить только Telegram**; Discord/Slack/WhatsApp/Signal/Email/Teams/Google Chat выключить.
- Выключить/не тянуть: desktop-app (`apps/`), web-UI (`web/`), `website/`, `optional-mcps`,
  `optional-skills`, `plugins`, cron-планировщик, subagents, batch/trajectory-инструменты, voice-зависимости
  (на минимальном extra, не `.[all]`).
- Learning loop / автонавыки / Honcho — для демо не нужны (и создают непредсказуемость); оставить фиксированный сценарий.
- Dashboard (хранит API-ключи) — только localhost/за SSH-туннелем, наружу не публиковать.

## 4. Адаптация под парк (VPS 8 GB, конвенции OpsHub)

- **Форм-фактор:** `hermes gateway` — always-on инфра-демон уровня OpsHub/tg-mcpd (одна LLM-сессия за раз,
  инференс в облаке ⇒ RAM хоста растёт умеренно). Но **установочный след тяжелее** FlowDesk:
  Python+Node+много зависимостей, Docker-образ крупный (s6-overlay). Диск 50 GB — ок.
- **Telegram:** у Hermes gateway **свой нативный Telegram** (бот). Это отдельный путь от `tg-mcp` (§5.6):
  для бот-туннеля Hermes самодостаточен; `tg-mcp`/`tg-mcpd` нужен только если требуется работа от
  **пользовательского аккаунта** (MTProto, 48 инструментов). Для демо достаточно нативного Telegram Hermes.
- **LLM:** BYOK-провайдер парка (`hermes model` → OpenAI-совместимый endpoint / Gemini-прокси); без GPU.
- **Конвенции OpsHub:** контейнер с label `demo=true`/`mem_limit`/heartbeat, но с оговоркой — gateway лучше
  держать «тёплым» (как tg-mcpd), а не lazy, чтобы не терять входящие сообщения. Решить при интеграции.
- **Маскирование PII** перед облачным LLM (§6); ключи — только в env/секретах, не в логах.

## 5. Вердикт

**Мощно, но тяжеловесно и с широкой атакующей поверхностью.** Для роли «ограниченный демонстратор сценария»
(как описано в `Контекст_…md`) Hermes — **избыточен**: это полноценный автономный агент, а нам нужен
предсказуемый бот с фиксированным сценарием и стопами перед действиями.

Два варианта (решение — за продуктом):

1. **Взять Hermes** как оркестратор ради его нативного мульти-платформенного gateway и зрелого рантайма —
   но **обязательно** в жёстко залоченном виде (safe-mode без terminal, whitelist toolset, approval, isolation,
   только Telegram, BYOK). Вендоринг кода — нет; установка внешней зависимостью с pin-версией + тонкий конфиг в репо.
2. **Не брать Hermes**, а написать **маленький собственный оркестратор** (Python + вызовы облачного LLM +
   `tg-mcp` для Telegram + JSON-контракты инструментов демо) — меньше кода, предсказуемее, безопаснее для
   публичного контура. По объёму сопоставимо с тонким конфигом поверх Hermes, но без 212 МБ чужого рантайма.

**Рекомендация:** для *публичного демо* на парке — вариант 2 (свой тонкий оркестратор) как более
безопасный и лёгкий; Hermes — держать как опцию для *приватного пилота/внедрения у клиента*, где нужны
полноценные агентские возможности и его gateway, на выделенном контуре.

По ВПС-ограничениям: **реализуемо** (LLM в облаке, без GPU, gateway как инфра-демон), но по установочному
следу и безопасности Hermes — самый «дорогой» кандидат из рассмотренных; свой оркестратор дешевле и предсказуемее.

> Проверка сборки/установки (`uv`/npm, Docker-образ) — на Node/Python-стеке при деплое; в текущем окружении недоступно.
