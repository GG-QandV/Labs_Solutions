# Контекст: AI Automation Lab / лендинг живых демо

## Цель проекта

Создаётся не SaaS «продажа токенов», а лендинг‑витрина **рабочих AI‑автоматизаций для бизнеса**. Ценность для клиента: увидеть процесс на живом демо, затем заказать аудит, проектирование, внедрение, интеграцию, настройку, развёртывание и сопровождение. Большинство компонентов должны быть open‑source/self‑hosted; клиент платит за работу и адаптацию под свои процессы.

ЦА: SMB и компании с документооборотом, продажами, CRM, поддержкой, логистикой, отчётностью, внутренними знаниями. Отдельно релевантен логистический кейс: международные перевозки, Китай–Европа/США/Украина, инвойсы, CMR, packing lists, заявки, отчёты.

## Позиционирование лендинга

Главный оффер:

> Показываю работающие AI‑автоматизации на реальных сценариях и внедряю их в ваши процессы, документы и сервисы. Большинство компонентов — open‑source. Вы платите за анализ, настройку, интеграцию и поддержку.

Лендинг должен показывать не «чат с AI», а контролируемые процессы:

```text
Входящие данные
-> извлечение / проверка
-> правила бизнеса
-> AI-обработка
-> human approval
-> результат: CRM, письмо, PDF, задача, отчёт
```

Обязательные акценты:

- AI не действует бесконтрольно: критичные действия подтверждает человек.
- Все результаты проверяемы: исходный файл, raw‑данные, статус, источник, confidence.
- Можно начать с простого демо и масштабировать до отдельного клиентского контура.
- Чувствительные данные можно маскировать перед отправкой в облачную LLM.


## Формат сайта

```text
Публичный лендинг
├─ Главная: оффер, кейсы, схема, CTA
├─ Каталог рабочих демо
├─ Отдельные страницы решений
├─ Интерактивные демо-сервисы
├─ LLM-чат по кейсам / FAQ
├─ Регистрация
├─ API для зарегистрированных пользователей и их агентов
├─ Страница безопасности и BYOK
├─ Форма discovery / заявка на внедрение
└─ Stripe: бронирование времени, аудит, этапы работ
```

Для клиента нужна короткая discovery‑форма: отрасль, текущий процесс, число клиентов, объём документов/страниц, количество встреч/звонков, используемые системы, требования к приватности, желаемый результат. Это нужно для обоснованного выбора стека и оценки внедрения.

## Коммерческая модель

- Бесплатный просмотр кейсов и ограниченные публичные демо.
- Платное: аудит процесса, архитектура, интеграция, настройка, развёртывание, поддержка.
- Stripe нужен не для продажи «AI‑кредитов», а для резервирования времени, предоплаты этапа, invoice/checkout.
- BYOK — дополнительная опция для пилота или внедрения, не основной продукт.
- Для каждого демо должна быть CTA: **«Проверить на своих данных»**, **«Обсудить внедрение»**, **«Получить оценку процесса»**.


## Выбранные 4–6 демо

Главная идея: не строить 15 независимых приложений. Сделать 5 взаимосвязанных модулей, которые можно демонстрировать отдельно или объединить в один pipeline.


| Приоритет | Демо-модуль | Вход | Результат | Почему нужен |
| :-- | :-- | :-- | :-- | :-- |
| 1 | AI‑диспетчер заявок | Email, форма, Telegram, текст | Структурированная заявка, приоритет, недостающие данные, черновик ответа, задача | Самый простой и понятный бизнес‑кейс |
| 2 | OCR + извлечение полей | PDF, scan, image, invoice, CMR, договор | JSON‑поля, проверки, confidence, статус | Очень наглядно, сильный логистический/документный кейс |
| 3 | RAG с источниками | Документы, OCR‑текст, инструкции, прайсы | Ответ + файл/страница/фрагмент источника | Демонстрирует работу с корпоративными знаниями |
| 4 | Генератор КП / PDF‑отчётов | Карточка заявки, таблица, документные поля | Фирменный PDF, email‑черновик, export | Материальный результат, понятный руководителю |
| 5 | CRM‑copilot / follow‑up | Лид, переписка, документы, статус | Summary, next step, задача, письмо на утверждение | Закрывает цикл продажи/обработки |
| 6 | Аналитик CSV/XLSX | Таблица или Google Sheet | Расчёты, графики, аномалии, текстовое объяснение | Отдельная витрина для руководителя/финансов/маркетинга |

Не включать в первую волну: browser‑agent, полностью автономные агенты, live speech translation, Google Ads‑аналитику, контент‑фабрику. Они могут быть отдельными vertical‑демо позже, но сложнее, менее стабильны или слабее показывают системную интеграцию.

## Главный демонстрационный pipeline

Сквозной сценарий — «Обработка клиентского запроса и подготовка коммерческого результата».

```text
1. Клиент вставляет письмо / заявку
   -> AI-диспетчер выделяет услугу, контакт, сроки, задачу, риски

2. Клиент прикладывает PDF / инвойс / договор
   -> OCR извлекает текст и структурированные поля
   -> валидатор отмечает ошибки и сомнительные данные

3. RAG ищет правила, прайс, FAQ, условия или инструкции
   -> возвращает подтверждённые фрагменты и источники

4. CRM-copilot создаёт lead / задачу
   -> предлагает следующий шаг и черновик ответа

5. Генератор PDF
   -> создаёт коммерческое предложение / клиентский отчёт
   -> сотрудник просматривает и вручную подтверждает отправку
```

На UI нужен видимый pipeline‑bar:

```text
Получено -> Извлечено -> Проверено -> Найдено в базе
-> Подготовлено -> Ожидает подтверждения -> Отправлено
```

Это ключевой визуальный элемент: клиент понимает, что это не один «промпт», а управляемая автоматизация.

## Роль Hermes

Hermes — не «всемогущий автономный агент», а текстовый демонстратор и оркестратор заранее ограниченного сценария.

Он должен:

- принимать demo‑input;
- проговаривать текущий шаг человеческим языком;
- вызывать разрешённые API‑инструменты;
- показывать structured result;
- указывать, каких данных не хватает;
- останавливаться перед критичными действиями;
- не отправлять письма, не изменять CRM, не принимает финансовых/юридических решений без подтверждения.

Пример реплики:

> Получен запрос на перевозку. Я определил маршрут, тип груза и ориентировочный срок. Для расчёта не хватает веса и Incoterms. После уточнения я создам черновик сделки, проверю приложенный инвойс и подготовлю предложение для утверждения менеджером.

Для Hermes заранее нужен `skill`/сценарий с фиксированными этапами, JSON‑контрактами инструментов и текстами объяснения.

## Техническая архитектура

### Базовый слой

```text
Cloudflare Pages
-> публичный лендинг и статические страницы

Cloudflare Workers / API gateway
-> регистрация, rate limit, demo session, API routing

VPS / Docker
-> тяжёлые демо-модули по запросу
-> OCR, RAG, Qdrant, workers, document processing

Shared services
-> PostgreSQL: пользователи, сессии, jobs, audit, metadata
-> object storage: исходные файлы
-> Qdrant: RAG vectors
-> queue: фоновые задачи
-> observability/logging
```

На VPS постоянно активны только reverse proxy, launcher/orchestrator, PostgreSQL и минимальные служебные процессы. Сервисы конкретного демо поднимаются при открытии его страницы и выгружаются после inactivity timeout. Цель — одновременно держать в памяти максимум 2–3 контейнера.

### RAG/документы

```text
Файл
-> object storage: оригинал
-> OCR / text extraction
-> PostgreSQL: текст, metadata, статус
-> chunking + embeddings + reranking
-> Qdrant или Weaviate
-> answer with citations
```

Не использовать RAG без цитат. Ответ без подтверждаемого источника считается ошибкой либо должен возвращать «в базе нет подтверждения». Предпочтение: Qdrant/Weaviate, embeddings + reranking + NER в Docker; graph‑слой — поздний этап, не MVP.

### Логика обработки

- Детерминированные расчёты, правила, суммы, проверки — кодом/SQL.
- LLM — для извлечения, классификации, редакции, объяснения, summary, черновиков.
- Все LLM‑результаты, влияющие на бизнес, проходят schema validation.
- Значимые внешние действия — только через human approval.
- Raw‑результаты не перезаписываются AI‑редактурой; чистовая версия и журнал изменений хранятся отдельно.


## Cloudflare PDF‑демо

Первый быстрый работающий шаблон:

```text
Публичная ссылка на Google Sheet
+ изображения из Google Drive
-> проверка структуры, объёма, скрытых данных, ссылок, изображений
-> adapter sheetsToReportJSON()
-> ReportJSON
-> HTML/PDF engine
-> preview
-> ручная кнопка «Сгенерировать»
-> email пользователю
```

Google Sheets/Drive — только временная заглушка источников на этапе демо. В production это заменяется собственным dashboard, БД и файловым хранилищем без изменения PDF‑engine, потому что входной контракт — `ReportJSON`.

Требования к PDF‑демо:

- Не использовать hardcoded business data.
- Пользователь сам вставляет публичную ссылку на таблицу.
- Сервис валидирует CSV/таблицу, объём, обязательные поля, hidden/visible ratio, изображения.
- Генерация запускается только отдельной ручной кнопкой.
- Один шаблон сначала, затем возможность добавлять.
- Минималистичный брендируемый PDF: placeholders «Ваш логотип», «Название компании».
- Поддержать готовые PNG/SVG диаграммы из Google Sheets/LibreOffice/другого источника.


## Модель и качество

Качество демо зависит от подключённой LLM. Поэтому pipeline и provider должны быть разделены:

```text
Business workflow
-> Model/provider adapter
-> Claude / OpenAI / Gemini / Azure OpenAI / Bedrock / local endpoint
```

Режимы UI:

- **Демо‑режим** — ограниченная модель/ключ платформы, тестовые данные.
- **Качественный режим** — пользователь подключает свой API‑ключ.
- **Корпоративный endpoint** — Azure OpenAI, Bedrock, private gateway.
- **Локальный endpoint клиента** — OpenAI‑compatible API в его контуре.

Сильные модели применять для сложного извлечения, договоров, RAG‑ответов, редакции и КП. Дешёвые модели/правила — для маршрутизации, классификации, JSON‑валидации, дедупликации, извлечения простых полей.

## BYOK и доверие

Нельзя обещать «ключ гарантированно нигде не появляется», если он вводится в ваш backend. Корректная формулировка:

> Ключ не хранится в открытом виде, не передаётся во frontend‑код, не записывается в логи или аналитику и используется только для разрешённых вызовов выбранного провайдера.

Режимы:


| Контекст | Режим | Где ключ |
| :-- | :-- | :-- |
| Публичное демо | Ваш ограниченный demo‑key | Отдельный demo project |
| Закрытый пилот | Ephemeral BYOK | Только RAM изолированной session‑worker, TTL 30–60 минут |
| Регулярная cloud‑работа | Encrypted BYOK | Шифрованно: DB + Vault/KMS, расшифровка только на вызов |
| Чувствительные данные/enterprise | Local connector | Только в контуре клиента |

Правила для BYOK:

- Только HTTPS POST body.
- Не использовать URL, cookie, localStorage, frontend config, analytics, debug/access logs.
- Маскировать ключ в UI.
- `Revoke` удаляет ключ из session memory.
- Отдельный тестовый ключ с маленьким spend limit, созданный клиентом.
- Логи содержат только событие `key_used/revoked`, но не значение ключа.
- Для production предпочтителен local connector: клиент запускает контейнер/агент, ключ остаётся на его инфраструктуре.


## Безопасность и данные

Целевая зрелая архитектура:

```text
Raw file store отдельно
-> OCR/text PostgreSQL отдельно
-> RAG vector store отдельно
-> metadata + tenant isolation
-> masking/NER перед cloud LLM
-> cloud LLM only when policy permits
-> audit logs + security controller
```

Предпочтительный двухмодельный подход для чувствительных данных: локальный слой маскирует персональные/идентифицирующие данные, сильная облачная модель выполняет семантическую обработку обезличенного контента; затем локальный слой восстанавливает допустимые значения. Для высокочувствительных данных полностью облачную обработку отключать.

## Страницы лендинга

1. **Главная** — оффер, проблемы, схема «данные -> AI -> контроль -> результат», CTA.
2. **Демо‑каталог** — карточки 5–6 сервисов, запуск теста.
3. **Страница pipeline** — единый сквозной сценарий с интерактивной лентой.
4. **RAG / OCR / CRM / PDF / Analytics** — отдельные страницы кейсов.
5. **Как внедряем** — discovery, аудит, MVP, интеграция, обучение, поддержка.
6. **Безопасность и BYOK** — схемы данных, ключи, облако/локально, human approval.
7. **API для агентов** — OpenAPI, тестовый ключ, безопасные demo‑endpoints.
8. **Заказать аудит / забронировать время** — Stripe checkout.
9. **FAQ / LLM‑чат** — отвечает только по вашим кейсам и документации.

## API‑слой

После регистрации пользователь получает ограниченный API‑ключ. UI и API используют один backend.

```text
POST /api/v1/demos/leads/classify
POST /api/v1/demos/documents/extract
POST /api/v1/demos/rag/query
POST /api/v1/demos/reports/generate
POST /api/v1/demos/analytics/analyze
GET  /api/v1/jobs/{id}
```

Позже поверх тех же tools можно сделать MCP server. Это превращает сайт в интерактивную лабораторию и API‑шлюз для пользовательских агентов, а не просто лендинг.
